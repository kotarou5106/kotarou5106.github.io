*研究回顾：2026 年 10 月—11 月初*

这份梳理记录了两个 Coding Agent 项目的初始设计、实验过程、研究转向及最终成果。两项工作分别围绕三个层次展开：项目一研究如何在有限预算内复用历史状态、提高轨迹采样效率；项目二最初试图从真实轨迹中学习局部动作价值，后来进一步完成真实强化学习训练系统。本文重点解释每个阶段的研究目的、实际观测及转向依据，并区分工程能力、算法效果与尚未验证的假设。

---

## 一、项目一：Adaptive Rollout Engine

### 1. 初始设计

项目一是 **Adaptive Rollout Engine for Agentic RL**。我们最初希望提高 Coding Agent 强化学习所需的轨迹采样效率，而不是直接提出新的 Actor 优化算法。

传统 Coding Agent 的一次 Rollout 通常从初始任务开始：读取任务描述、调查仓库、搜索相关函数、尝试修改、运行测试，最后提交补丁。即使多个 Rollout 处理的是同一个任务，每条轨迹也可能重复大量相同的前期调查。问题因此变成：**既然 Agent 已经调查过代码并到达有价值的中间状态，为什么下一次尝试还必须从头执行？**

例如，Agent 花费多次模型调用定位了问题函数，但第一次修复失败。这时最有价值的资源未必是从头再生成一条轨迹，而可能是已经保存的“定位完成、尚未错误修改”的状态。

因此，项目一的基本设计是保存真实的中间状态，允许从某个 Checkpoint 启动相互独立的 Continuation，并在有限预算内决定是从根状态采样、从中间状态分支，还是继续当前轨迹。

### 2. 同状态恢复

为了让不同 Continuation 能够从真正相同的历史状态出发，我们实现了可核验的 Checkpoint 保存与恢复机制。它不仅记录 Agent 的消息历史，还保存 Git 基准提交、已暂存与未暂存修改、未跟踪文件、工具反馈、已消耗的模型调用与预算，以及配置和完整性哈希。

这里最重要的是**同状态恢复**：不同分支不仅需要看到相同的历史消息，还必须面对相同的仓库文件状态，并继承相同的历史执行进度和预算约束。恢复时，系统从指定 Git 基准提交重建工作树，再加载对应的 Agent 状态，而不是简单地把历史对话重新输入模型。

在此基础上，不同 Continuation 分别运行于独立的 Sandbox，保证后续代码修改和工具执行不会相互污染。最终补丁还会进入干净环境进行独立评分，避免原始执行环境中的残留状态影响奖励。

这使得同一个历史状态可以被重复用于不同的后续探索，也为项目二的受控动作比较与失败恢复提供了基础。

### 3. 预算调度

能够保存与恢复 Checkpoint 后，还需要回答：有限的调用预算应该分配给哪个状态？如果对所有候选状态平均采样，可能重复消耗资源；如果只选择看起来最接近成功的状态，又可能忽略尚未充分探索的分支。

我们因此提出前缀价值估计，描述给定状态和剩余预算下继续执行的成功可能性：

$$
V(s,b)=P(R=1\mid s,b)
$$

其中 `s` 是保存的历史状态，`b` 是剩余执行预算。**预算控制（Budget Control）** 是这个估计的核心约束：一次探索会消耗模型调用、Token、费用和时间，因此调度器不仅要判断哪个状态值得继续，还要衡量在当前剩余预算下继续探索是否划算。我们结合历史观测、Checkpoint 特征、逻辑回归预测、预算匹配与不确定性信息，形成候选状态的成功潜力估计。

调度器据此选择三种动作：**BRANCH** 从已有 Checkpoint 启动独立分支，**CONTINUE** 继续现有轨迹，**STOP** 在预算或合法条件不满足时结束。系统持续记录调用、Token、费用、执行时间和真实奖励；恢复 Checkpoint 时继承历史资源消耗，避免重新启动分支后绕过原有预算限制。

完整执行链路为：真实代码任务 → mini-SWE-agent 执行 → Checkpoint 保存与恢复 → Root/Fixed/Adaptive 调度 → 独立 Continuation → 补丁评分与结果归档。

### 4. 实验结果

我们在 3 个 SWE-bench Pro 任务、3 个随机种子下比较了三种策略。每种策略完成 54 个终点动作，共计 162 个。

| 策略 | 成功次数 | 成功率 | 每次成功摊销模型调用 |
|---|---:|---:|---:|
| Root Uniform | 9/54 | 16.67% | 71.67 |
| Fixed Branching | 28/54 | 51.85% | 23.14 |
| Adaptive | 30/54 | 55.56% | 21.37 |

最明确的结果是，在这批任务中，从历史 Checkpoint 采样的 Fixed 与 Adaptive 均明显高于重复从根状态采样的 Root。Adaptive 相比 Root 的成功率提高约 38.89 个百分点，每次成功所需模型调用降低约 70.19%。Adaptive 只比 Fixed 多成功两次，在这个样本规模下尚不能证明它具有稳定的统计优势。

正式实验存在两种合理的费用口径：实际物理执行约 **1,826 次模型调用、1.7137 美元**；按照公平比较协议将共享历史前缀分别计入不同策略后，约为 **1,934 次模型调用、1.7987 美元**。差异来自真实运行中可以复用同一前缀，而比较策略成本时需要把前缀成本分别摊回各自方案。

### 5. 工程成果

项目一完成了**同状态恢复、独立分支与预算受控的真实 Rollout 采样**，并建立干净环境中的终局补丁评分。它没有直接训练 Actor，但使同一个历史状态可以被重复使用，并为后续不同动作的 Continuation 提供可靠的工程起点。这也是项目二最初能够开展 Trajectory Critic 研究的基础。

## 二、项目二：原始设计

### 1. 信用分配

项目一解决了如何采样的问题，但如果我们已经获得大量成功与失败轨迹，下一步如何利用它们训练模型？

Coding Agent 的一条轨迹可能先阅读报错、定位正确函数、完成接近正确的修改，随后又覆盖此前修改，最后提交失败。整条轨迹的终局奖励仍然是零：

$$
R(\tau)\in\{0,1\}
$$

这就是 **信用分配问题（Credit Assignment Problem）**：终局奖励只反映整条轨迹最终是否成功，并没有直接区分各个中间动作的价值。

我们希望利用项目一的分支能力，学习一个 **动作价值函数（Action-Value Function）**：

$$
Q^{\pi}(s,a)=\mathbb{E}_{\pi}[R\mid s,a]
$$

其中 `s` 是当前状态，`a` 是选择的动作，`π` 是之后固定的执行策略。这个量表示从当前状态执行某个动作、再按照后续策略继续执行时的期望终局回报。

与项目一的区别在于：**项目一主要估计一个状态值不值得继续探索，项目二则希望比较同一个状态下不同动作的价值。** 前者主要服务于采样预算分配，后者开始直接服务于 Actor 的策略学习。

### 2. 三组实验方案

我们最初规划的是三组强化学习对照，而不是孤立训练一个 Critic。A、B、C 只是实验组代号，其中 C 组是我们希望验证的 Trajectory Critic 增量；它们并非三个独立项目。

| 组别 | 方法 | 要检验什么 |
|---|---|---|
| A | CISPO | 基础策略优化能否在真实 Coding Agent 环境工作 |
| B | CISPO + GiGPO | 局部环境分组优势能否提供额外收益 |
| C | CISPO + GiGPO + Trajectory Critic | 学习得到的动作价值信号能否在 B 上继续提高成功率与样本效率 |

**CISPO（Clipped Importance Sampling Policy Optimization，截断重要性采样策略优化）** 负责真正的模型参数更新；**GiGPO（Group-in-Group Policy Optimization）** 用环境状态分组构造局部优势；**Trajectory Critic（轨迹评价模型）** 是我们想检验的增量研究创新。

因此，**C 相比 B 的独立增益，才是原始 C 线的核心指标。** 如果 C 比 A 更好，却没有超过 B，那么收益可能完全来自 GiGPO，无法证明 Critic 增加了有价值的信息。

而且，即使 Critic 能够预测历史轨迹的成功率，也不意味着它一定能帮助 Actor 学习。最终还需要把 Critic 信号接入真实强化学习，在独立任务上比较成功率、样本效率和额外计算成本。

### 3. CISPO 与 GiGPO

项目二的 A 组使用轨迹级中心化优势。对于同一任务中的 `N` 条轨迹，令 `R_i` 为第 `i` 条的终局奖励，则：

$$
A_E(\tau_i)=R_i-\frac{1}{N}\sum_{j=1}^{N}R_j
$$

例如四条轨迹奖励为 `[1, 0, 0, 0]`，对应优势为 `[0.75, −0.25, −0.25, −0.25]`。成功轨迹具有正优势，失败轨迹具有负优势，模型据此调整生成动作的概率。

CISPO 使用重要性采样比率（Importance Sampling Ratio）衡量当前策略与记录行为策略的差异：

$$
r_t=\exp\left(\log\pi_{\theta}(a_t\mid s_t)-\log\mu(a_t\mid s_t)\right)
$$

其中 `μ` 是采样时的行为策略，`π_θ` 是当前待更新策略。其更新过程用截断重要性采样权重和给定优势加权动作的对数概率梯度，并处理 Token Mask、数值异常及有效 Token 归一化。

但 CISPO 本身不能保证使用的优势已经正确反映了各个中间动作的贡献。于是我们引入 GiGPO，尝试利用多条轨迹中重复出现的环境状态，计算更加局部的回报差异。

在最终实现里，A 组使用轨迹级优势 `A_E`，B 组使用：

$$
A_{\mathrm B}=A_E+A_S
$$

其中 `A_S` 是环境状态分组产生的局部优势。GiGPO 改变的是优势信号，不是把 CISPO 的参数更新机制替换掉。

但是，我们后来遇到一个重要问题：**环境状态相同，不代表完整 Agent 决策状态相同。** 两条轨迹的 Git 文件可能完全一致，但模型历史消息、已经阅读的文件、工具反馈和剩余预算不同。仅凭仓库状态就把两次决策当成完全相同的状态，未必足以构成严格的动作价值对照。

这个问题后来贯穿了 GiGPO、Trajectory Critic 审计与 RTMC 分析。

### 4. Critic 的增量信号

我们最初设想训练一个参数化 Critic，使其估计动作条件价值，并进一步构造局部优势：

$$
Q_{\phi}(s_t,a_t)\approx Q^{\pi}(s_t,a_t),\qquad
A_C(s_t,a_t)=Q_{\phi}(s_t,a_t)-V_{\phi}(s_t)
$$

然后把动作条件化的局部优势加入 B 组训练。关键不是增加一个会打分的模型，而是 Critic 是否学到了 **GiGPO 原本无法提供的动作差异信息**。

如果 Critic 只是预测哪个任务比较容易，或者把更长的消息当成更好的动作，它仍然没有回答“在同一个状态下究竟应该选哪个动作”。

因此，最初的研究假设是：通过同状态不同动作的受控 Continuation 学习可靠的动作价值，再将 Critic 的局部优势加入 CISPO + GiGPO，有望进一步提高真实任务成功率或样本效率。后续的历史数据采集与受控实验，就是为了检验 Critic 是否具有这样的判别能力。

## 三、Trajectory Critic 实验

### 1. 数据采集

为了检验此前提出的 Critic 假设，我们复用项目一的 Checkpoint 分支能力，从相同历史状态生成不同 Continuation，保留真实工具反馈和终局奖励，再用这些记录训练动作价值模型。这里的检验重点不再是轨迹能否产生，而是 **Critic 能否可靠地区分同一状态下的候选动作**。

最终累计整理了 855 条历史 Continuation，覆盖 25 个任务、10 个仓库，其中包含 82 组同状态、不同首动作、终局成功与失败不同的历史偏好对照。

| 数据              | 数量    |
| --------------- | ----- |
| 历史 Continuation | 855 条 |
| 覆盖任务            | 25 个  |
| 覆盖仓库            | 10 个  |
| 不同历史状态          | 565 个 |
| 成功与失败混合的状态      | 84 个  |
| 不同首动作的成功—失败对照   | 82 组  |

这些记录保留了完整历史与真实终局评分。82 组对照的已记录 Checkpoint、仓库状态、对话历史和预算匹配，说明状态恢复本身已经成功；困难在于能否从这些样本中学到稳定的动作排序能力。

### 2. 模型评价

早期 Trajectory Critic 在整体终局分类任务上取得了约 0.849 的 AUROC（Area Under the Receiver Operating Characteristic Curve，受试者工作特征曲线下面积）。

AUROC 衡量的是模型区分正负样本的能力。忽略评分相同的情况时，其概率解释是：随机选取一条成功轨迹和一条失败轨迹，模型给成功轨迹更高分数的概率：

$$
\mathrm{AUROC}=P\bigl(f(X^+)>f(X^-)\bigr)
$$

其中，`X⁺` 和 `X⁻` 分别是成功、失败轨迹，`f` 是模型评分。

但 AUROC 允许跨任务、跨状态比较。例如，某些任务本来就容易成功，另一些则普遍失败；模型只要识别任务难度，就可能取得较高的整体 AUROC，而没有真正判断过同一状态下两个动作孰优孰劣。**我们需要的是同状态动作排序能力，而不只是终局成功分类能力。** 因此，接下来直接使用 82 组历史成功—失败偏好进行评价。

具体来说，给定同一个状态下的两个候选动作，如果 Critic 给最终成功一侧更高的分数，就记为一次排序正确。

我们将数据按照仓库隔离，划分为训练集 52 组、验证集 21 组、测试集 9 组，并与简单的 Shallow 逻辑回归模型进行比较。

| 模型                | 验证集          | 测试集        |
| ----------------- | ------------ | ---------- |
| Trajectory Critic | 9/21（42.9%）  | 6/9（66.7%） |
| Shallow 逻辑回归      | 10/21（47.6%） | 5/9（55.6%） |

这里的 Shallow 是我们设置的简单基线，使用二元逻辑回归（Binary Logistic Regression）预测轨迹的终局成功概率。它不分析代码语义，而是使用消息长度、消息数量、工具调用次数、测试和补丁命令标记、剩余预算等九项统计特征。

其预测形式为：

$$
P(R=1\mid x)=\frac{1}{1+e^{-z}}
$$

其中：

$$
z=\beta_0+\sum_{j=1}^{9}\beta_j\frac{x_j-\mu_j}{\sigma_j}
$$

这里，x_j 表示第 j 个输入特征，μ_j 和 σ_j 分别表示训练集上该特征的均值和标准差，β_j 是模型通过训练得到的权重。

训练时，我们最小化带有 L2 正则化的加权二元交叉熵损失：

$$
\mathcal{L}=-\frac{1}{N}\sum_{i=1}^{N}w_i\left[y_i\ln p_i+(1-y_i)\ln(1-p_i)\right]+\frac{\lambda}{2}\sum_{j=1}^{9}\beta_j^2
$$

其中，y_i 是轨迹最终成功或失败的标签，p_i 是预测成功概率，w_i 是样本权重，正则化系数为 λ = 0.02。

由于每组历史对照的初始状态、历史上下文与预算相同，九项特征中实际上只有两项影响组内排序：完整可见消息的 JSON 字符数，以及工具调用数量。

根据训练得到的参数，两个候选动作 A、B 的线性得分差可以写成：

$$
\Delta z\approx 0.17715\ln\frac{1+L_A}{1+L_B}+0.06162(C_A-C_B)
$$

其中，L 表示消息的 JSON 字符数，C 表示工具调用次数。由于 Sigmoid 函数严格单调，当 Δz > 0 时，Shallow 就认为动作 A 对应的轨迹更可能成功。

这意味着，Shallow 根本不需要理解模型读取了什么代码、修改了什么函数，就可以依靠消息长度和工具调用次数完成排序。

复杂 Critic 在验证集上比 Shallow 少判断正确一组；测试集多正确一组，但仅有九组样本，无法据此建立稳定优势。**它并未展现出超越简单统计特征的可靠动作价值排序能力。**

后来我们又进行了更严格的 7B 受控动作实验，从相同状态执行不同的候选动作，获得真实的回报差异。但这些实验集中于 `boltons` 仓库的少数修复任务，训练出的 Critic 在留出任务上的排序效果仍然不理想。

例如，一次受控实验的留出开发集排序正确率为 25%，测试集为 50%，仍然没有表现出可靠的动作价值泛化能力。

### 3. 阶段性决策

**停止的直接原因，是我们实际训练出的 Critic 动作排序能力不足。** 历史偏好评价没有稳定超过 Shallow；更严格的受控动作实验虽然获得回报差异，却仍未验证模型能够在留出任务上可靠泛化。现有 Critic 尚不足以作为 CISPO + GiGPO 的可信增量训练信号。

继续研究本来可以通过扩大受控数据、调整监督方式并重新评价来推进，但这些工作需要新的实验投入。我们于 **2026 年 10 月 27 日**作出阶段性 No-go 决策，停止原定的 Critic 增量强化学习实验；这不是 Checkpoint 失败，也不意味着动作价值学习在理论上不可行。

此后，我们转而利用已经保存的失败轨迹、工具反馈和 Checkpoint，研究一个更直接的问题：失败之后从哪里恢复，才能更有效地完成任务？

## 四、第一次转向：Failure-Aware Recovery

### 1. 研究动机

Failure-Aware Recovery（失败感知恢复）研究的是**恢复位置选择**：面对一条已经失败的真实 Agent 轨迹，能否利用其中的工具反馈和历史 Checkpoint，选择一个更值得重新尝试的位置？

例如，Agent 已经调查了大量代码，随后做了一次错误修改。如果能够恢复到错误修改之前，就可能保留此前有用的调查信息，同时重新尝试修复，不必从头再来。

这一阶段比较的是恢复策略，不涉及 Critic 学习或 Actor 参数更新。

### 2. 恢复策略对照

我们直接复用了项目一的 Checkpoint 加载、仓库恢复、Sandbox 执行及独立评分能力。比较三个组：

| 策略 | 做法 |
|---|---|
| Restart | 从任务初始状态重新执行 |
| Random Recovery | 在合法历史恢复点中随机选择 |
| Failure-Aware Recovery | 根据首次工具失败、编辑行为等过程证据，采用预设启发式规则选择恢复点 |

这里的真实恢复 Actor 使用 **DeepSeek Flash API**，不是 Qwen 7B。三个组比较的是恢复策略，不涉及模型参数训练。

我们实际执行 **8 个任务 × 3 组 = 24 条新轨迹**，其中 23 条获得有效评分。7 个任务三组全部有效，可直接比较：

| 策略 | 成功任务 | 追加模型费用 |
|---|---:|---:|
| Restart | 3/7 | $0.08489 |
| Random Recovery | 4/7 | $0.08792 |
| Failure-Aware Recovery | 4/7 | $0.10100 |

Failure-Aware 与 Random 的成功任务完全一致，但 Failure-Aware 的追加模型费用高约 **14.9%**。

### 3. 失败分析

失败分析表明，Failure-Aware 组三个失败任务都没有在预算内产生有效修复补丁，而是在持续调查中耗尽调用次数。选择新的恢复点，没有自动改变 Actor 反复调查、迟迟不提交修改的行为。

此外，“首次工具失败”可能只是搜索命令没有匹配内容，并不一定是导致任务失败的关键错误；当时合法恢复点又主要集中于早期调查阶段，并没有充分检验“回滚错误修改、保留此前正确修改”这一更有价值的场景。

因此，这次实验验证了真实 Checkpoint 恢复与续跑能够工作，但**没有验证我们设计的启发式恢复点选择优于随机恢复**。

### 4. 成功恢复数据

虽然恢复位置策略没有表现出优势，实验却产生了 **9 条成功恢复后缀，覆盖 5 个任务和 5 个仓库**。这意味着一些原本失败的任务，在重新恢复执行后产生了真正的成功行为。

虽然恢复位置选择没有取得优势，但成功后缀提供了可用于监督学习的实际动作序列。下一阶段因此转向检验这些数据能否改善模型的失败恢复行为。

## 五、第二次尝试：Failure-Aware SFT

### 1. 恢复示范

失败后重新修复成功的后缀，可能包含普通成功轨迹不容易覆盖的行为，例如读取失败反馈、改变调查方向、纠正此前假设、再次修改并执行测试。

因此，我们尝试通过 **监督微调（Supervised Fine-Tuning，SFT）**，直接让模型学习这些恢复成功时实际执行的下一步动作。与 Trajectory Critic 不同，SFT 不先估计动作价值，而是使用历史上下文与对应成功动作构造监督目标。

### 2. 监督数据对照

我们使用 Qwen2.5-Coder-7B-Instruct，比较：

| 组别 | 训练数据 |
|---|---|
| Success-only | 普通成功轨迹 |
| Success + Recovery | 普通成功轨迹加成功恢复后缀 |

这里比较的是两种 SFT 数据来源，不是前面 CISPO/GiGPO 的策略优化对照。

研究问题是：在相同训练预算下，恢复成功轨迹能否提供超过普通成功轨迹的额外训练价值？

### 3. 监督配方修正
第一轮 SFT 完成后，我们发现监督数据构造存在三个问题，分别涉及上下文截断、动作目标选择和工具协议匹配。

首先是**上下文截断**。 一条成功恢复轨迹往往包含大量历史调查、工具输出和代码修改记录，而训练窗口最多只能容纳 8,192 个 Token。如果直接保留完整历史，许多真正重要的后期修复动作就无法进入训练窗口。我们最初检查发现，这种情况下只有 17 个恢复动作、1,538 个监督 Token 能够保留下来，而且没有包含实际编辑命令。后来我们调整了上下文构造方式，优先保留任务信息、最近的完整动作与工具反馈，对较早、较长的工具输出进行压缩，同时确保当前监督目标是完整的。

其次是**动作目标选择**。 一条轨迹最终成功，不意味着其中每个动作都值得模型模仿。最初的筛选规则没有充分识别真实文件修改，反而保留了大量调查操作。在后来的完整审计中，我们发现九条成功恢复后缀实际上包含 15 个生产源码修改回合，而早期配方只选中了其中 2 个，漏掉了另外 13 个。更严重的是，有些命令虽然尝试修改文件，但工具反馈已经明确表明替换失败；模型真正纠正错误的后续动作却可能没有被选中。因此，我们重新结合文件变化、工具反馈和执行记录判断动作是否有效，避免把失败的修改当成正向监督，同时保留真正完成修复和后续验证的动作。

最后是**工具协议匹配**。第一轮训练后，Qwen 7B 经常不能按照 Agent 执行器要求的 JSON 格式生成 Bash 工具调用，导致命令无法执行。第二轮我们将训练目标与实际调用格式对齐，由执行器预先提供固定的工具调用前缀，让模型主要学习命令参数及完整 JSON 的结束部分，从而减少无效格式监督。

因此，第二轮不仅重新筛选了训练动作，还修复了上下文窗口和工具调用格式问题，并进一步控制两组的训练任务、监督 Token 与实际输入 Token 数量，使恢复数据的增量效果能够得到更直接的比较。

最终两组各使用 **4,096 个监督目标 Token，执行 2 次优化器更新**，实际完整上下文输入均约 **139,445 Token**。严格对照训练数据只覆盖两个任务、两个仓库，训练范围很小。

独立评估结果：

| 模型 | 成功任务 |
|---|---:|
| Base | 0/4 |
| Success-only | 0/4 |
| Success + Recovery | 0/4 |

因此，这次没有观察到普通成功数据或恢复成功数据带来的独立修复成功率改善，更没有证明 Success + Recovery 优于 Success-only。

### 4. 阶段性结论

第二轮已解决监督构造中最明显的截断、动作遗漏和格式不匹配问题，但独立任务仍没有出现成功率增量，而严格可比训练数据仅覆盖两个任务。继续扩大这条路线需要新增成功恢复样本和更多付费训练。我们因此没有继续追加 SFT，而是把重心放回一直并行开发的真实 Actor 强化学习系统。

## 六、早期强化学习：Qwen 7B

项目二从一开始就规划了 CISPO/GiGPO 的真实 Actor 训练；Trajectory Critic、失败恢复和 SFT 是与这条工程主线交叉推进的研究工作。此前虽然运行了大量真实 Coding Agent 轨迹，但**真实 Rollout、监督微调和完成强化学习更新是不同的事情**。要理解最后为什么更换执行配置，需要先看早期 7B 系统实际停在了哪里。

### 1. 强化学习闭环

完整的 Coding Agent 强化学习至少需要形成以下循环：

**Actor 生成 Rollout → 真实环境评分 → 计算优势与 CISPO/GiGPO 损失 → 反向传播并更新 Actor 参数 → 使用更新后的 Actor 继续采样。**

仅仅生成轨迹、获得二元奖励，并不能说明模型完成了强化学习。此前各阶段的工作性质如下：

| 阶段 | 主要工作 | 参数更新性质 |
|---|---|---|
| 项目一 | 真实 Rollout、Checkpoint 分支、独立评分 | 不更新 Actor |
| Trajectory Critic | 855 条历史轨迹、82 组偏好及 Critic 训练 | 更新 Critic，不更新 Actor |
| Failure-Aware Recovery | 24 条恢复策略对照轨迹 | 不更新模型 |
| Failure-Aware SFT | 使用成功轨迹微调 Qwen 7B | 监督学习，不是 RL |
| 早期 1.5B CISPO | 真实奖励、优势、反向传播、参数更新 | 完成小规模 RL 机制验收 |
| 早期 Qwen 7B RL | 多步轨迹采样、评分、概率校准 | 正式 A/B 在参数更新前停止 |
| 最终 mini-coder-4B | 采样、评分、参数更新、再次采样 | 完成正式多轮 RL |

这意味着早期并非没有做过真实强化学习：**Qwen2.5-Coder-1.5B-Instruct 已经通过混合精度、奖励驱动 CISPO 更新与 Checkpoint 恢复等验收**。但小模型机制通过，并不代表使用 7B 模型执行真实多步代码修复时，也能稳定获得训练信号并完成连续更新。

### 2. 初始 Actor 与工具协议

正式研究最初选择 **Qwen2.5-Coder-7B-Instruct**。其基础模型版本已经固定在 revision `c03e6d358207e414f1eca0bb1891e29f1db0e242`，权重分片及 Tokenizer 也经过身份核验，因此这里不存在前面远程 DeepSeek API 的版本不可验证问题。

当时的 7B Actor 使用自建 READ、EDIT、TEST 等结构化工具接口，特别是 EDIT 要求模型严格指定修改目标、内容和执行动作。真实运行发现，模型常常输出不符合协议的编辑，引用不存在的符号，缺失函数体，或反复调查而未能形成有效补丁。这里既有模型行为问题，也有执行接口设计的限制，不能简单断言“7B 本身不会修代码”。

项目一事实上已经使用 mini-SWE-agent、Harbor、Sandbox 和 Checkpoint 解决了大量真实执行问题；项目二早期再次开发结构化工具体系，相当于重新承担工具解析、编辑语义和异常反馈的维护成本。后续逐步统一原生 Bash 执行链路，正是为了减少这种重复实现。需要说明，Failure-Aware SFT 分支此前也使用过 Bash JSON 目标，统一工作是逐步完成的，并非只有一次协议切换。

### 3. 执行结果与奖励稀缺

在一批早期 7B 训练采样中，**24 条轨迹全部得到有效的零奖励**。按同任务中心化终局优势计算，如果组内所有轨迹都失败，那么对应的轨迹级优势就是零：

$$
R_1=R_2=\cdots=R_N=0\quad\Longrightarrow\quad A_E=0
$$

如果相关环境分组也没有回报分化，局部优势同样为零。这时即使训练代码能执行反向传播，也没有来自该批优势的有效更新信号。

后续另一批 32 条真实 7B 校准轨迹，虽然成功了一条，但有 30 条耗尽调用预算，且出现大量 EDIT 执行错误：

| 指标 | 实测结果 |
|---|---:|
| 校准轨迹 | 32 |
| 成功修复 | 1 |
| 预算耗尽 | 30 |
| EDIT 工具执行错误 | 117 次 |
| 解析失败 | 55/349 次决策 |

大量调用被无效工具交互或持续调查消耗，能够用于训练的奖励分化仍然稀缺。**这不是轨迹没有真实执行，而是执行后的奖励很难形成有用的策略学习信号。**

### 4. 行为概率校验

除了奖励稀缺，CISPO 训练还遇到另一个独立问题：采样时记录的行为概率，与训练时重新计算的概率没有达到预先规定的数值一致性要求。

为什么要计算两次？**采样时**，Actor 按 Token 逐步生成动作，通常使用键值缓存（Key-Value Cache，KV Cache）复用此前的注意力计算；系统记录每个已生成 Token 的对数概率。**训练时**，模型需要对这些已经生成的 Token 重新执行可微分的前向计算，才能形成对当前参数的梯度。因此，训练器把已知序列重新送入模型，利用因果注意力掩码（Causal Attention Mask）计算对应位置的概率，并不要求模型再次随机生成同一条轨迹。

两条路径对应的是同一条件概率，只是计算形式不同：

| 项目 | 采样阶段 | 训练阶段 |
|---|---|---|
| Token 计算 | 逐步生成，复用 KV Cache | 对已记录序列进行前向计算 |
| 是否重新采样动作 | 是，生成新 Token | 否，重算已生成 Token 的概率 |
| 是否需要梯度 | 不需要 | 需要 |
| 固定模型与输入时的理论概率 | 相同 | 相同 |

不同的 GPU 注意力实现、浮点精度或计算顺序可能带来数值偏差。我们检查的是两条路径对**同一批已生成 Token**的对数概率差，而不是两次随机生成的文本是否相同：

$$
\Delta_{\max}=\max_t\left|\log p_{\mathrm{sample},t}-\log p_{\mathrm{recompute},t}\right|
$$

这项检查与 CISPO 的重要性采样比率直接相关：

$$
r_t=\frac{\pi_{\theta}(a_t\mid s_t)}{\mu(a_t\mid s_t)}
$$

其中分母是采样行为策略概率，分子是训练阶段计算的当前策略概率。在参数更新之前，如果模型身份和输入一致，比率理论上应接近 1；过大的重算偏差会干扰重要性采样权重的准确性。

早期一次 24 条采样后的最大误差约为 **0.13054**；随后 32 条校准的最大差异为 **0.16787**。两次都超过了我们预先冻结的 **0.1** 门槛：

$$
\Delta_{\max}=0.16787>0.1
$$

因此训练程序在正式参数更新前停止。已确认的是两条计算路径存在超过阈值的偏差，并没有最终定位某个特定 GPU 算子是唯一原因。这一问题与模型代码修复能力、DeepSeek 版本控制问题也都不同。

### 5. 阶段结论

早期 Qwen 7B 正式 A/B 被阻断，实际原因是两类困难同时存在：一方面，工具协议错误与预算耗尽使成功奖励及组内优势稀缺；另一方面，行为概率重算没有通过数值检查，无法放心进入参数更新。即使分别修复其中一个问题，也不代表另一个会自动消失。

我们没有删除错误 Token、修改历史概率或放宽预定阈值来强行启动训练。因此，**Qwen 7B 阶段有真实 Rollout、评分和训练校准，却没有完成预期的多轮 CISPO/GiGPO 更新**。这成为最终调整 Actor、工具链与训练配置的直接背景。

## 七、最终训练：mini-coder-4B

在停止 Critic 增量研究、完成恢复和 SFT 尝试后，我们把重心重新放回项目初始就规划的 **CISPO/GiGPO 强化学习对照**。这一阶段有两个明确目标：其一，在真实 Coding Agent 环境中完成能够连续采样、评分并更新参数的训练闭环；其二，比较 CISPO 与 CISPO + GiGPO，检验环境状态分组的局部优势能否改善真实任务成功率和样本效率。

最终不再加入 Trajectory Critic，因为当时的 Critic 尚未表现出可靠的动作排序增量。mini-coder-4B 和原生 Bash 并不是新的算法研究目标，而是为了完成这项正式训练而调整的执行载体。

### 1. 实验配置

我们需要在明确记录行为策略身份的条件下采样，再用这些轨迹更新参数，从而形成同策略强化学习（On-policy Reinforcement Learning）的真实闭环。为此，我们没有继续沿用早期 Qwen 7B 与自建 READ/EDIT/TEST 的正式配置，而是同时调整模型和执行方案。

| 维度 | 原 Qwen 7B 方案 | 最终正式方案 |
|---|---|---|
| Actor | Qwen2.5-Coder-7B-Instruct | `ricdomolm/mini-coder-4b` |
| 模型规模 | 约 7B | 约 4B |
| 工具接口 | 自建 READ/EDIT/TEST | mini-SWE-agent 原生 Bash |
| 任务 | 早期冻结的修复合同 | SWE-bench Verified |
| 执行预算 | 较短的决策与上下文限制 | 最多 60 次工具调用、65,536 Context |
| 环境 | 早期工具交互与隔离体系 | 统一 Sandbox Bash 执行链路 |
| 策略更新 | 7B 正式对照在校准阶段阻断 | CISPO + LoRA + AdamW |
| 恢复机制 | 既有 Actor Checkpoint | 模型、优化器、随机状态及概率身份一致性核验 |

**这并非只更换模型规模。** 模型、工具接口、任务分布、预算和训练运行方式均发生变化，因此无法用前后两批结果直接比较 7B 与 4B 的代码修复能力；我们实际验证的是新配置能够完成多轮训练。

### 2. 预算与工具链

此前许多 7B 轨迹在持续调查和格式错误中耗尽预算，尚未形成有效补丁便结束。因此，我们将正式执行预算扩大至最多 60 次工具调用、65,536 Token 上下文，给 Agent 更充分的调查、修改和验证机会。扩大预算会增加成本，也不保证成功，但可以减少过早结束造成的零奖励样本。

原生 Bash 则减少了对自建 READ/EDIT 严格格式的依赖，并复用项目一已有的真实 Shell、Git、Sandbox、Checkpoint 与独立评分能力。这不仅改变了 Agent 的调用方式，也减少了两套执行环境重复维护的成本。

### 3. M 阶段验收

在正式 A/B 之前，我们先做了定向机制验收 M，检查真实代码执行、独立评分、优势、LoRA 更新、Checkpoint 恢复是否构成完整闭环。

M 阶段调度 **24 条**，全部取得有效评分，其中 **19 条成功**，并完成 **2 次有效参数更新**。但 M 使用了定向选择的训练任务，目的是机制验收，不是独立泛化实验。

我们没有把 M 阶段权重和成功轨迹混入正式 A/B 的共同初始化与指标统计。

### 4. 训练设计

正式对照保留两个研究组：

```text
A = CISPO
B = CISPO + GiGPO
```

原计划的 Critic 增量组未参与本次正式训练。

模型为固定 revision 的 `ricdomolm/mini-coder-4b`，冻结 32 个训练任务、12 个独立评估任务，训练与评估按照仓库隔离。两组从相同的基础模型、LoRA、优化器及随机状态开始，但使用两张独立的 48GB GPU 分别执行，不是把两张卡作为同一模型的数据并行训练。

每组四轮，每轮 32 条调度记录，总计每组 128 条。Agent 通过 mini-SWE-agent 执行真实 Bash 命令，完成代码修改后提取终态补丁，由独立评分器生成二元奖励。随后根据有效评分计算优势，执行 CISPO 更新，并保存模型和优化器状态供下一轮使用。

### 5. 参数更新

| 指标 | A：CISPO | B：CISPO + GiGPO |
|---|---:|---:|
| 调度记录 | 128 | 128 |
| 有效独立评分 | 72 | 69 |
| 有效成功轨迹 | 23 | 25 |
| 有效参数更新 | 3 | 3 |

总计 **256 条正式 Rollout 调度记录、141 条有效独立评分、115 条未评分、6 次有效参数更新**。

两组第一轮都没有形成非零有效优势，正确跳过参数更新；后三轮均完成非零梯度、LoRA 参数改变和 Checkpoint 核验。这里的 6 次更新是真实模型更新，不是仅计算 Loss 或模拟反向传播。

但训练轮次的成功数量不能直接连成学习曲线：四轮使用不同任务，实际有效评分数量也不相同，不能把“某一轮成功更多”直接解释为模型比上一轮学得更好。

### 6. 缺失评分

256 是正式调度记录数，**不是 256 条全部完成并取得终局评分的轨迹**。其中 115 条没有有效评分，占 44.92%。

未评分原因包括任务准入失败、推理服务拒绝连接或中断、Actor 工具命令超时、独立 Verifier 超时等。其中只有五条属于采样完成后独立评分超时，其余还包含执行中断或准入失败。

必须区分：

```text
Reward = 0     ：已有效评分，任务修复失败。
Reward = null  ：没有可信的最终评分，原因可能是执行/环境中断。
```

不能把 null 自动填成零，否则会把执行异常当成模型失败，并可能污染优势计算。A、B 的有效评分数也不相同，所以这不是一个完全理想、没有缺失干扰的算法消融实验。

### 7. 独立评估

在双方都获得有效独立评分的 10 个任务上，A 成功 1 个，B 成功 2 个：一个任务双方都成功，一个任务只有 B 成功，其余八个任务双方失败。

精确双侧 McNemar 检验给出 `p = 1`。这个结果当然不足以证明 GiGPO 在独立任务上具有可靠、稳定的泛化优势。

三方 Base/A/B 共同有效的九个任务上，成功数分别是 1、1、2。另有一项值得注意的观察：Base、A 第一轮和 B 第一轮拥有相同的模型权重，因为第一轮没有参数更新，但它们在个别任务上的执行结果仍然不同。

这说明真实并发 Agent 执行中，即使固定权重和根 Seed，也不保证工具交互轨迹逐步完全一致；单次结果差异不能自动归于模型学习。

### 8. 局部优势审计

B 组确实计算出了非零的 GiGPO 局部优势 `A_S`，并实际将它加入 CISPO 的训练系数。所以不能说 GiGPO 没有参与参数更新。

但进一步审计发现，真正非初始仓库状态上的非零 `A_S` 主要集中于 B 第三轮的一个 Django 任务、一个环境投影组，包含 45 个决策。虽然这些决策具有相同的仓库状态投影，却拥有 **45 个不同的可见历史上下文或预算签名**。

更重要的是，非零 `A_S` 没有激活原本 `A_E` 为零的新训练 Token 支持集，而主要改变已有非零优势 Token 的权重。

因此，**GiGPO 的局部系数重加权确实发生并参与了更新，但我们没有证明它提供了严格相同完整 Agent 状态下新增的动作信用分配证据。**

这并不等于 GiGPO 实现错误。按环境投影分组是它实际采用的算法口径；更严格的完整状态等价，是我们为了检验“局部动作价值”提出的更高证据要求。

### 9. 阶段成果

本阶段完成了真实 Coding Agent 的连续采样、工具执行、独立评分、行为概率记录、CISPO/GiGPO 优势计算、LoRA 参数更新，以及模型、优化器与随机状态的保存恢复。**基础 Agentic RL 工程闭环已经建立；GiGPO 的独立性能增益仍未获得证实。** 这两项结果分别对应本阶段的工程目标和算法对照目标。

## 八、补充工程与分析

这些工作不是新的第三次、第四次研究转向，而是围绕已完成的系统，处理真实轨迹数据质量、自动测试反馈与局部价值分析问题。

### 1. Trajectory Wash

真实 Rollout 中有工具异常、测试失败、评分缺失、重复调查及信息不完整的轨迹。如果只保留成功轨迹或非空补丁，可能丢掉有研究价值的失败行为和完整的同状态对照。

因此，我们实现轨迹解析、首次可观察失败点、过程证据检查、数据评分、时间顺序约束、配额与整组偏好保留。一个重要原则是：评价某个动作时，不能把动作发生之后才知道的最终结果提前当成当时已知的信息。

对 **1,111 条记录**进行分析，在相同保留 352 条的预算下：

| 指标 | 简单基线 | Trajectory Wash |
|---|---:|---:|
| 保留轨迹 | 352 | 352 |
| 保留完整历史偏好对照 | 5 组 | 26 组 |
| 覆盖任务 | 15 | 25 |

但 Wash 选集只保留了 114 条成功轨迹，而简单基线保留 308 条。它更适合强调比较结构与覆盖面的研究目标，不等于对所有 Success-only SFT 都更好。

### 2. Test-in-Loop

真实 Coding Agent 有时修改代码后不及时运行相关测试，或者没有利用测试失败反馈继续修复。因此，我们在原生执行链路中加入自动测试反馈：检测文件变更、选择相关公开测试、执行真实 Shell/unittest，再将结果注入 Agent 的工具观察，由同一 Actor 决定是否继续修改。

系统还包括超时、测试次数、总预算、重复控制与 Checkpoint 状态持久化。

最终完成 **13/13 个真实本地机制验收场景**，包括两次“测试失败—继续修复—复测通过”的闭环。Actor 行为由确定性本地程序驱动，真实 Shell 和测试命令确实执行；这验证了工程机制，并不等于完成了新的 4B 模型成功率提升实验。

### 3. RTMC

虽然我们停止了参数化 Trajectory Critic，局部信用分配问题并没有消失。正式 RL 获得新的真实轨迹后，我们尝试在不训练新 Critic 的情况下，使用轨迹树和蒙特卡洛回报计算状态与动作价值。

这就是 **Rollout-Tree Monte Carlo（RTMC，轨迹树蒙特卡洛）**。

核心是利用已有轨迹的真实回报估计：

$$
\begin{aligned}\hat Q(s,a)&=\frac1{N(s,a)}\sum_{i\in\mathcal D(s,a)}G_i\\\hat V(s)&=\frac{\sum_a N(s,a)\hat Q(s,a)}{\sum_a N(s,a)}\\\hat A(s,a)&=\hat Q(s,a)-\hat V(s)\end{aligned}
$$

但这样做又回到了最初的状态等价难题：什么情况下两条轨迹真的处于相同状态？如果只比较仓库文件，可能忽略模型历史和剩余预算；如果要求完整上下文一致，又几乎找不到足够的中间状态重合。

我们分析了 **141 条有效评分轨迹、5,599 个决策**，建立状态签名、动作签名、前缀树和多种匹配口径。宽松状态抽象能找到一些中间态分叉与非零回报差，但严格可见上下文与预算匹配下，仍没有新增可信的非初始状态信用证据。

因此，RTMC 完成了离线实现与分析，但没有接入新的 Actor 更新。它进一步说明：**训练系统完成后，原始 C 线所缺的严格动作价值监督并不会自动出现。**

### 4. 受控续跑归档

我们还检查并归档了已有的受控动作续跑与 Checkpoint 恢复代码，准备从固定历史状态注入不同动作进行比较。相关本地确定性恢复链验收已经完成，但没有新增正式付费 4B Continuation，也没有执行 Critic C 组的 RL 训练。

这应当被归类为研究基础与离线准备，而不是已完成的新算法结果。

在 10 月 31 日至 11 月 1 日，我们整理了工程指标、轨迹质量、复现说明、README、技术报告与求职材料。重点是严格区分真实 GPU 参数更新、有效独立评分、离线数据分析、本地确定性机制验收，以及尚未执行的研究计划。

## 十、研究转向的判断

回顾几次调整，重要的是分清**算法假设没有取得效果、数据来源发生变化和工程系统无法通过准入**这三种不同原因。各阶段的判断如下：

| 调整 | 直接依据 | 实际决策 |
|---|---|---|
| Trajectory Critic → Failure-Aware Recovery | 历史与受控评价中的 Critic 动作排序没有表现出可靠增量 | 暂停追加 Critic 训练，转向利用现有失败轨迹研究恢复点 |
| Failure-Aware Recovery → Failure-Aware SFT | 启发式恢复未优于随机恢复，但获得 9 条成功后缀 | 改为检验成功恢复数据能否改善 Actor 的监督学习 |
| Failure-Aware SFT → 正式 Agentic RL | 修正监督配方后独立评估仍无改善；基础 RL 系统也亟待完成 | 停止扩大 SFT，优先完成 CISPO/GiGPO 的真实多轮训练 |
| Qwen 7B → mini-coder-4B 配置 | 原配置在执行、优势和行为概率校准上无法稳定通过 | 同时调整模型、原生 Bash、任务、预算和训练链路 |

其中，**第一次转向不是技术上被迫放弃 Trajectory Critic**。我们完全可以增加受控数据、固定策略并重新训练，但当时的 Critic 判断能力没有达到预期，继续投入的理由不足。最后也没有在完成 4B A/B 后重新追加 Critic 组，因为 RTMC 仍未找到充分的严格中间状态动作监督，而项目已经转入工程交付与求职阶段。这些是阶段性研究决策，不是对动作价值学习的普遍否定。

## 十一、成果与证据边界

### 1. 工程成果

项目一完成了 Checkpoint 保存与恢复、独立续跑、预算调度、真实补丁评分。项目二进一步完成了真实 Agent 轨迹采样、工具执行、行为概率记录、CISPO/GiGPO 优势计算、LoRA 参数更新以及模型/优化器恢复。在此基础上还完成了 Wash、Test-in-Loop 与 RTMC 的相应实现和验收。

### 2. 实验结果

项目一的分支采样在正式任务上明显优于反复从根状态采样；Adaptive 比 Fixed 略高，但未证明稳定的统计优势，修复后的在线奖励调度机制也没有重新进行完整付费实验。

项目二的历史与受控实验表明：从相同状态采取不同动作确实可以产生回报差异，但少量结果筛选后的成功—失败偏好不足以可靠估计可迁移的动作价值。Failure-Aware 恢复没有超过随机恢复，恢复成功数据的 SFT 未提高独立任务成功率。最终 CISPO/GiGPO 完成真实模型更新，但 GiGPO 的稳定增益未得到验证。RTMC 进一步发现严格中间状态比较仍然稀缺。

### 3. 未验证的假设

原始 Critic 增量的核心假设，是在相同成本和独立任务评价条件下：

$$
\mathrm{CISPO+GiGPO+Critic}>\mathrm{CISPO+GiGPO}
$$

正式 Critic 增量组没有运行，因此这个关系仍属于未验证假设；4B 中 GiGPO 多成功的一个任务，也不足以建立普遍增益。评价必须继续区分：真实参数更新是否发生、算法增益是否观察到，以及增益是否达到可信的独立验证水平。

## 十三、最终认识

两个项目实际处理的是同一条研究链路上的不同环节。项目一首先让 Coding Agent 的历史中间状态成为可复用的资源，并在有限预算下决定如何采样；项目二则尝试判断这些轨迹中的动作是否具有可靠的局部价值，以及怎样把终局奖励用于更新策略。因此，**生成轨迹、估计动作价值、完成参数更新**是三个不同的技术任务，前一项成立不保证后一项自然成立。

我们最初对 Trajectory Critic 的期待，是凭借可恢复的同状态分支获得足够可靠的动作监督。然而，已有 Critic 的排序能力没有达到预期；Failure-Aware Recovery 和恢复 SFT 也分别取得了真实执行证据，却没有验证出算法上的额外收益。随后，Qwen 7B 阶段暴露出多步工具执行与概率校准的困难，促使我们调整模型和执行配置，最终完成了 mini-coder-4B 的 CISPO/GiGPO 多轮训练。训练系统已经形成工程闭环，但可信的非初始状态动作监督仍然稀缺，原始 Critic 增量假设也未获得验证。

最终，**项目一的主要成果是状态化、预算受控的真实 Rollout 采样；项目二的主要成果是可执行、可评分、可恢复、能真正更新 Actor 的 Agentic RL 系统，以及围绕局部信用分配留下的可复核实验记录。** 这既是我们当初研究计划的延续，也是实际实验不断修正后的结果。
